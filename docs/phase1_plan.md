# Phase 1 计划书（10/29 – 11/4）

## 一句话目标

让老师看到：**很多 agent 共用一张小显卡时，吞吐到底被什么卡住了**：
是 KV 不够用、agent 等工具时白占着 KV，还是 KV 被挤掉以后要重算。

---

## 现在到哪了

**已经能用的**
- 整条链路在本机真 GPU 上跑通：agent → 工具 → llama-server → 打分 → 日志。
- 结果可复现：Windows 上重新生成的数据和 workload 与 Mac 逐字节一致。
- 指标都采得到：每个请求的 token 数、缓存命中、TTFT，GPU 显存，工具等待时间。
- 第一组观察：1.5B 时 agent 有 67–75% 的时间在等工具；把并发 K 从 1 提到 4，吞吐涨到 3.3 倍。

**场景还有 4 个问题要先修**（用 7B smoke 的 12 个任务逐条核对后发现的）

| # | 问题 | 通俗解释 | 怎么修 |
|---|---|---|---|
| 1 | **"长上下文"其实不长** | `react_long` 最后只有 2.1–2.7k token，和 `react_short`（1.9–2.2k）差不多，设计要求是 4–8k。原因：只有搜中标题时才返回长段落，没搜中只返回几个建议标题，而大部分搜索都没搜中。`oneshot_long` 也只有 1.1–1.5k。 | `react_long` 搜不中时，也附上 BM25 最相关的几段正文；`oneshot_long` 在题目自带的 10 段之外，再加一些 BM25 检索到的干扰段落 |
| 2 | **"长输出"其实不长** | `react_explain` 要求写 150–250 词的解释，模型实际只写 1–2 句（约 30 token），512 的上限一次都没用到 | few-shot 示例里换成真正的长解释；或者在 finish 之后单独加一步"写答案报告" |
| 3 | **太多任务没做完就被强制交卷** | 12 个任务里有 5 个走到了步数上限：模型反复换说法搜同一个东西，最后答"没找到信息" | 加"重复动作提示"；同一个搜索词第二次出现时，直接告诉模型换方向 |
| 4 | **一个格式小 bug** | 模型写成 `Action  finish[...]`（漏了冒号），被判成格式错误，任务直接失败 | 解析时允许冒号缺省（一行正则） |

**为什么要先修：** 课程要求负载里有"短/长上下文、短/长输出"的混合，现在所有任务都差不多是"约 2k 上下文、约 40 token 输出"。不修的话：
- 长任务和短任务没区别，H3（驱逐长任务比驱逐短任务代价大得多）就测不了；
- 质量太差的话，goodput（每分钟答对的任务数）没有意义。

另外有一个**发现，不算 bug**：共享前缀（system prompt 加 few-shot 示例）占了每个 agent 上下文的 57–76%。如果每个 slot 都各存一份，KV 大部分都花在重复的内容上了，E0 要专门查这一点。

## 交给老师什么

1. **报告**（`docs/phase1_report.md`），重点是：
   - 场景和负载怎么设计的，可以怎么复现；
   - baseline 是怎么做的；
   - 5 张图：E1–E5 各一张；
   - **一段有数据支撑的结论：瓶颈是哪一个，在什么条件下成立。**
2. **代码和一键复现命令**：冻结的 workload，以及每次运行记录的 `meta.json`（版本、模型、哈希）。
3. **"质量没有变差"的证据**：每张性能表都同时列出完成数、F1 和输出长度。

> 老师最看重的是**把一个瓶颈讲清楚**，不是图多。E1、E3、E5 加上一段清楚的结论，比十张没有结论的图更有用。
