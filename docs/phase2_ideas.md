# Phase 2 方向（2026-11-18 确定）

## 0. 目标和指标

**在显存固定的边缘 GPU 上，让同样大小的 KV pool 每分钟完成更多任务，延迟更低，答题质量不变或只略降。**
课程要求贡献在 KV cache 的管理上，每个 cache 操作都必须用 llama.cpp 实际提供的控制（或我们公开说明的补丁）。

每次实验都按同一张表报告：

| 层级 | 指标 |
|---|---|
| 主指标 | goodput（每分钟 EM 答对数）、任务延迟 p95 / p99 |
| 请求级 | TTFT p50 / p95（排队 + prefill）、TPOT p50 / p95（每个输出 token 的 decode 时间） |
| 约束 | 完成数、失败数（overflow）、EM / F1（F1 变化在 ±0.03 内算持平；同一配置两次重复之间就会差这么多） |
| 解释 | KV 占用（平均 / 峰值）、闲置 KV 比例、重算 token 数、前缀缓存命中率 |

这些指标在 `summary.json`、`analysis/aggregate.py` 和 Grafana 看板（`tools/observability/`）里都有。

## 1. 确定的方向和顺序

**底座 → selective KV → 想法 B**，一步一步做：每一步做完、汇报、确认后再进下一步。

### 1.1 底座：按 KV 预算放任务，绝不超出 pool

- **解决什么**（Phase 1 E2）：上下文在任务中增长 2.3–4.2 倍，超出 pool 时所有在跑的请求一起失败，
  所以 fixed K 只能按最坏情况少放任务（8k / 16k pool 只有大 pool 吞吐的 48% / 80%）。
- **做法**（`edgeserve/kvm.py`、`edgeserve/policies.py`）：
  - 准入：按每类任务预测的峰值 KV 预留，总和 ≤ ρ × pool 才放进来；峰值先用 Phase 1 数据，运行中在线更新。
  - 发请求前检查：估算这次请求后 slot 的 token 数，放不下就先处理其他 slot（已结束任务的 KV → 等工具的
    agent 的 KV），仍放不下就让请求等待。绝不发出会导致 overflow 的请求。
  - 由管理器选择 slot，优先复用同类任务留下的 slot（保留 system prompt 的前缀缓存）。
  - system prompt 只存一份：我们给 llama-server 加的 fork 接口（`tools/llama_patch/fork_slot.diff`，
    底层是 `seq_cp`，只给 cell 加一个序列标记，不复制数据），X3 验证过输出一致。
- **状态**：已实现（策略 `base`、`base_fork`），16k pool 冒烟测试 0 次 overflow。11/17 用当时的组合配置
  （底座 + fork + 压缩 + 已删除的"清理闲置 KV"策略，ρ=2.0）测得 goodput 28.6，比 fixed K=4 的 21.1 高 36%；
  这个配置在 11/18 清理代码时拆掉了，正式数字要在底座这一步用 `base_fork` 重新测。
  还缺：按正式场景调参和重复实验。
- **新颖性**：低（InferCept、Continuum 做过 tool call 时的 KV 保留 / 丢弃），作为基础设施，不算主要贡献。
- **selective KV 依赖它**：显存压力的判断、"先裁剪、再整份丢弃"的顺序都在这里实现。

### 1.2 selective KV：按段选择保留哪些 KV，在 KV 里直接删除，不重算（主要贡献）

**状态（2026-11-18）**：第 1 步（可行性）和第 2 步（质量）完成，结果见第 4 节；第 3 步的场景已确认，见 §4.3。

**要回答的问题**：一个 agent 的 KV 里，哪些该留、哪些可以删，怎么删最便宜。

**依据**：
- Phase 1：`react_long` 检索回来的 token 只有 4.5% 是 supporting facts；KV 增长几乎全部来自检索结果。
- 阶段 1（见第 3 节）：一次检索平均增加约 860 个 token；去掉相关段落后 F1 不变，峰值 KV 减半，
  131k pool 下 goodput 从 23 涨到 45 /min，TTFT p95 2.2 s → 0.14 s，TPOT p50 38 → 20 ms。
  说明检索内容是 KV 浪费的大头，而且大部分删掉不影响答题。

**两个层面**：

| 层面 | 内容 |
|---|---|
| 执行机制（原 K2） | 给 llama-server 加一个"删除 slot 中指定范围的 KV"的接口：`seq_rm` 删除这段 cell，`seq_add` 把后面的 token 位置往前挪（重新施加 RoPE），再更新 slot 记录的 token 序列。llama.cpp 的 context shift 就是这样实现的（`tools/server/server-context.cpp:3858–3871`），我们只是把固定的"删 n_keep 之后一段"改成任意范围。补丁规模预计和 fork 相当。 |
| 选择策略 | 决定删哪些内容（见下）。 |

**设计空间**：
1. **粒度**：整条检索结果 / 段落 / 句子。不做逐 token（需要 attention 分数，llama.cpp 不对外提供，前人已做）。
2. **打分器**（判断内容还有没有用）：
   - oracle：HotpotQA 标注的 supporting facts，只作为效果上界；
   - BM25：句子和"问题 + 已写的思考"的相关度；
   - 被引用的实体：句子里的实体在后续思考中出现过就保留；
   - 时间先后：越早的检索结果越可能已经用完。
   - 四种打分器在 `edgeserve/selection.py`（`select_drop`；entity：句子里的大写词在后续思考中被提到过的个数），
     由 `edgeserve/kvtrim.py` 的 `SelectiveKV` 调用。
3. **触发时机**（memory-aware）：
   - agent 写完下一步思考之后（已经"读过"这段内容）；
   - 只在显存紧张时：和底座结合，显存不够时先裁剪等工具的 agent 的旧检索结果（不用重算），
     还不够再整份丢弃 KV（要重算）；显存宽松时不裁剪，质量不受影响。
4. **对照：改文本 + 重算**（`--selective text`，也是前人"截断旧工具输出"的做法）：删掉同样的句子，但只改 prompt，
   下一次请求从第一个改动处重新 prefill。
   在 KV 里直接删 vs 改文本重算，省多少时间、质量差多少，是本方向的核心对比之一。

**新颖性**：
- 前人的 KV 裁剪（H2O、SnapKV、StreamingLLM）针对单个请求，按 attention 分数逐 token 删，不知道 agent 的结构；
- 前人的 agent 上下文管理（Complexity Trap、PACE 等）改文本，需要重算；
- 我们利用 agent 结构，在 KV 层面按段删除，不需要重算，按显存压力触发，服务多个 agent。没有找到这样的组合。

**预期提升的指标**：每个 agent 占的 KV 变小 → 紧张 pool 下放更多任务（goodput）；pool 里 KV 总量变小 →
decode 每步读的数据更少（TPOT）；和整份丢弃相比不用重新 prefill（TTFT）。

**风险**：
1. 质量：后面 token 的 KV 是在"看过被删内容"的情况下算出来的，删掉后有不一致；位置平移会重新施加 RoPE。需要实测。
2. 实现：删除后，客户端下次发的 prompt 必须和服务器缓存的 token 序列完全对得上，否则前缀缓存失效、整段重算。
   被删内容的起止要精确落在 token 边界上，这是主要的工程难点。
3. 和 fork 的交互：共享的 system prompt 不能被删（只删 slot 自己的检索结果）。

**步骤**：
1. **可行性**（基本不用 GPU）：写补丁，解决客户端 token 对齐，验证删除后缓存命中正常、输出正常。
2. **质量实验**（pool 给足）：打分器 × 保留比例 → F1 和节省的 KV；同时和"改文本 + 重算"对比。
3. **serving 实验**（紧张 pool）：底座 vs 底座 + 按压力触发的 selective KV，按第 0 节的指标表报告。

### 1.3 想法 B：分组 KV pool，按 agent 的增长来分配和迁移

#### Phase 1 的依据
llama.cpp 只提供两个极端，各有一个 Phase 1 测出的缺点：

| 模式 | 优点 | 缺点（Phase 1 测量） |
|---|---|---|
| 共享 pool（`--kv-unified`） | 容量灵活，能吸收上下文增长 | 每步 decode 要读到 pool 里最高的已用 cell；K=32 时每 token 耗时 254 ms，吞吐下降（E1） |
| 每 slot 独立 KV | 每个 slot 只读自己的 KV；K=16 时快 27% | 每个 slot 容量固定为 `-c / np`，上下文增长 2–4 倍就放不下（E2） |

X1 微基准（`docs/phase2_notes.md` §6）：decode 每步 ≈ 13.0 ms + 0.127 ms × (KV 跨度 / 1k cell)，开销来自显存带宽。

#### 做法
1. **llama.cpp 补丁**：把 KV 分成 G 组，组内共享，组间独立。
   - 源码依据：`src/llama-kv-cache.cpp` 里的 `seq_to_stream` 就是"序列 → stream"的映射表。目前只允许 `n_stream == 1`（全部共享）或 `n_stream == n_seq_max`（每序列一个），见第 134 行的 assert 和第 147–152 行。
   - 改成 G 组，例如 `seq_to_stream[s] = s * G / n_seq`，看起来改动不大。
   - 多 stream 时，CUDA 的 mask scan 会按每个 stream 自己的末尾裁剪（`fattn-common.cuh`，条件是 `Q->ne[3] > 1`），所以每组只读自己的跨度。
2. **调度器**（扩展 `kvm.py`）：
   - 按每个 agent 的预测峰值做装箱，决定它进哪个组（哪些 slot id）；
   - 某组快满、其他组还有空间时，用 save → restore 把 agent **迁移**到别的组，代替丢弃 KV 后重新 prefill；
   - 用 X1 的代价模型选 G：G 越大，读的跨度越短；但每组容量越小，越容易需要迁移。
3. G=1 就是共享 pool，G=K 就是每 slot 独立 KV。我们要找中间最好的点，并证明按增长装箱 + 迁移比两个极端都好。

#### 为什么新
vLLM 这类分页系统没有这个问题，所以没人研究。但 llama.cpp 是边缘部署最常用的运行时，这是边缘场景专属的设计点，和课题里的 "edge" 直接对应。原方向 1（闲置 KV 拖慢 decode）并入这里，X1 的测量作为动机。

#### 要对比的东西
- 共享 pool + 最优 fixed K（Phase 1 E1：K=8 时 45.2 tasks/min）；
- 每 slot 独立 KV（Phase 1 E1b：K=8/16/32 时 43.0 / 54.8 / 64.5 tasks/min）；
- 分组但不迁移（只装箱）；
- 分组 + 装箱 + 迁移。
- 场景：充足 pool（131k，E1 场景）和紧张 pool（16k/32k，E2 场景）都要测。B 的卖点就是两种场景下都不差。

#### 风险
- **补丁可行性未验证**：多 stream 时 ubatch 怎么切分（`split_equal`）、每组的 KV 大小怎么算、server 是否假设 stream 数只能是 1 或 np，都需要看源码确认。
- 共享 system prompt（fork）只能在组内用，所以每组要存一份 prompt。
- 迁移用 save/restore，会阻塞所有 decode（Phase 1：3k token 约 119 ms）。

#### 实现成本
中到高。需要先花约 1 天看源码、做原型，确认补丁可行，再决定做不做。

## 3. 阶段 1 结果（2026-11-18）：检索档位的 KV 成本、性能和答题质量

设置：`react_long` 的四个检索档位，dev 200 题（每档相同题目），pool 131k（无显存压力），K=8，
fixed_k，每档 2 次重复。配置 `configs/sweeps/p2a_stage1.yaml`，分析 `analysis/obs_levels.py`，
结果 `results/p2a_stage1/levels.json`。ΔF1 为逐题配对（两次重复取平均）相对 L0 的差，bootstrap 95% CI。

**性能**（rep0）：

| 档位 | goodput | 吞吐 | 任务服务时间 p50 / p95 | TTFT p50 / p95 | TPOT p50 / p95 |
|---|---|---|---|---|---|
| L0（段落 + 9 个相关段落） | 23.0 /min | 44.1 /min | 9.6 / 21.7 s | 0.36 / 2.20 s | 38 / 90 ms |
| L2（只有段落） | 44.6 /min | 86.6 /min | 4.9 / 11.7 s | 0.07 / 0.14 s | 20 / 25 ms |

**KV 和质量**（两次重复合并）：

| 档位 | 检索返回 | F1（两次） | ΔF1 vs L0 [95% CI] | SF 覆盖 | LLM 调用 | 搜索次数 | 走到步数上限 | 一次检索 token p50 / p95 | 峰值上下文 mean / p95 | prefill / 任务 | 吞吐（131k, K=8） |
|---|---|---|---|---|---|---|---|---|---|---|---|
| L0 | 段落 + 9 个相关段落 | 0.623 / 0.640 | – | 0.83 | 3.58 | 1.96 | 12% | 858 / 1,655 | 3,428 / 5,215 | 1,925 | 44–46 /min |
| L1 | 段落 + 4 个 | 0.642 / 0.613 | −0.003 [−0.037, +0.030] | 0.83 | 3.54 | 1.89 | 12% | 577 / 844 | 2,712 / 4,154 | 1,210 | 62–64 /min |
| L2 | 只有段落 | 0.660 / 0.674 | +0.036 [−0.010, +0.084] | 0.74 | 3.78 | 2.27 | 13% | 131 / 244 | 1,926 / 2,518 | 418 | 86–87 /min |
| L3 | 段落前 3 句 | 0.616 / 0.636 | −0.005 [−0.060, +0.051] | 0.69 | 3.96 | 2.37 | 17% | 121 / 195 | 1,907 / 2,491 | 392 | 81–82 /min |

噪声：同一档位两次重复之间，9–15% 的题 F1 不同，平均 F1 相差最多 0.03（比 Phase 1 估计的 ±0.012 大）。
L1 的 2 个失败是同一道题两次都格式解析失败（agent 问题，不是系统故障）。

结论：
1. **检索内容是 KV 和延迟的大头，而且大部分可以去掉。** L0→L2 峰值 KV 降 44%（p95 降 52%），prefill 降 78%，
   goodput 和吞吐翻倍，TTFT 和 TPOT 大幅下降，F1 不变（L2 略高，但 CI 包含 0）。
   相关段落是 BM25 找来的干扰项，和 Phase 1 的"只有 4.5% 有用"一致。
2. **降到 L3 开始出现行为代价：** agent 多搜（1.96→2.37 次）、走到步数上限的比例 12%→17%，SF 覆盖 0.83→0.69；
   L3 不比 L2 省多少 KV，所以不划算。
3. **对方向的影响：** 想法 A 的"按压力自适应"没有收益空间；但"检索内容大多可删"直接支持 selective KV：
   与其一开始就少给内容，不如让 agent 完整读一遍，用完后在 KV 里删掉。

## 4. selective KV 结果（2026-11-18）

### 4.1 第 1 步：可行性（`bench/s1_trim_check.py`，详细数据见 `docs/phase2_notes.md` 末尾 S1）

在 KV 里按范围删除 token 可行：20/20 次成功，平均删掉 prompt 的 28%，删除耗时约 1.5 ms，
删除后下一个请求完全复用缓存（不重算），显存确实释放，fork 共享的 system prompt 不受影响。
92.7% 的句子能对齐到 token 边界（整段连标题删 + 起点吸附空格）。删除不缩短 attention 的跨度，
所以收益在容量（紧张 pool），不在 TPOT。

结论：
1. **质量守住了**：所有不依赖标注的配置 ΔF1 都在 ±0.03 内（CI 都包含 0）。recency 误删 supporting fact
   最多（247 句），F1 最低，风险最大。
2. **"用过即删"省得最多**：BM25 下峰值 p95 从 −17% 提到 −26%，KV·时间 −18%，F1 不变。p95 降得比平均值多
   （−26% vs −14%），因为搜得多的长任务删得最多，而准入正是按这些长任务的峰值预留。
3. **在 KV 里删优于改文本重算**（同样的句子）：F1 相同，但 text 方式每个任务多 prefill 18–27%，
   goodput 低 11–14%（21.1 vs 23.7；22.2 vs 25.7），TTFT p95 高 0.35–0.65 s，TPOT 高约 4 ms，
   而且 KV·时间反而更高（重算期间仍占着 KV）。
4. **宽松 pool 下 selective KV 不提升 goodput**（23.7–25.7 vs 24.0）：容量不是瓶颈，删除也不缩短跨度，
   和第 1 步的预期一致。收益要在第 3 步的紧张 pool 里看。
5. **删掉干扰内容可能反而提高准确率**：oracle 用过即删 F1 +0.053（CI 不含 0），与阶段 1 L2 的 +0.036 一致。
   说明更好的打分器有机会同时省 KV 和提质量（报告里可作为发现；不是本项目的主线）。

**第 3 步采用的设置**（按事先的规则：ΔF1 ≥ −0.03 的非 oracle 配置里峰值 p95 降得最多）：
**kv，BM25 保留 30%，用过即删（`--selective kv --sel-scorer bm25 --sel-keep 0.3 --sel-keep-last 0`）**。
注意：entity 没有测"用过即删"的版本，CI 宽度约 ±0.04，结论是"F1 下降不超过约 0.04"。

### 4.3 第 3 步设计（2026-11-18 确认；场景在 §4.4 改为 8k）：紧张 pool 下的 serving 实验

**为什么换场景**：第 2 步是"所有任务在 t=0 一次性进来、只有 `react_long`"，显存压力从头到尾不变，
最优做法永远是同一个固定策略，memory-aware 体现不出价值。第 3 步加入两个维度，让最优做法随显存状态变化：
1. **负载随时间波动**：突发到达（忙闲交替，`arrival: {type: bursty}`），闲时显存够用，忙时紧张；
2. **多任务混合**：Phase 1 默认混合，不同任务的显存占用和"能不能删"差别很大。

（"tool 延迟有长尾"和"删除分档、有质量代价"两个维度这次不加，留作以后的扩展。）

**场景**：

| 项目 | 设置 |
|---|---|
| 任务混合 | `react_short` 40% / `react_long` 30% / `react_explain` 20% / `oneshot_long` 10% |
| 到达 | 突发到达，平均到达率 3 档：约为容量的 50% / 80% / 110%（容量先在 dev 上测出） |
| 显存 | 16k pool 为主，时间允许再加 32k |
| 题目 | dev 用于调参（fixed K*、ρ*、到达率），test 用于最终结果 |
| selective KV 设置 | 第 2 步选出的：kv，BM25 保留 30%，用过即删 |

**配置**：

| # | 配置 | 回答什么 |
|---|---|---|
| 1 | fixed K*（dev 上调到最优） | Phase 1 基线 |
| 2 | 底座（`base_fork`：按 KV 预算准入 + 共享 system prompt，ρ* 在 dev 上调） | 只靠准入能做到多少 |
| 3 | 底座 + selective KV，改文本重算（`--selective text`） | 前人做法，对照 |
| 4 | 底座 + selective KV，在 KV 里删，一直删 | 我们的方法 |
| 5 | 底座 + selective KV，在 KV 里删，只在显存紧张时删 | memory-aware 的触发方式是否更好（需要实现） |

底座按已完成任务的实际峰值在线更新预测峰值，所以开启删除后 `react_long` 的预留会自动变小，准入能放进更多任务。

**指标**：goodput、任务延迟 p95/p99（含排队）为主；TTFT、TPOT；完成数、失败数、F1（**分任务类型**：第 2 步只验证了
`react_long`，`react_short` 和 `react_explain` 删了会不会掉分要在这里检查）；KV 占用随时间的变化（Grafana 可直接看
忙时 / 闲时管理器的反应）。

**报告的讲法**：KV 管理器按代价从低到高收回 KV：先在 KV 里删已用过的检索内容（约 1.5 ms，不重算），不够再整份丢弃
（要重新 prefill），最后让新任务排队。配置 4 和 5 是"删除阈值"这一个参数的两个取值（0 和压力阈值）；按第 2 步的数据，
预计一直删最好，即"删已用内容几乎没有代价，最优做法是尽早删；高代价的丢弃仍只在显存紧张时做"。

**流程**：
1. 准备（2026-11-23 完成）：配置 5 的触发方式 `--sel-trigger pressure`（KV 管理器报告压力时才删：有任务排队等准入 / 等显存，
   或 pool 占用超过 85%；不删的检索结果不标记，之后压力出现时再一起删，推迟次数记为 `trim_deferred`）；
   工作负载 `p3_mixed_dev200`（调参，t=0 全部放入）和 `p3_mixed_dev60_bursty`（流程检查）；mock 上 5 种配置
   各 60 个任务全部完成、0 overflow、四类任务都正常。调参配置 `configs/sweeps/p3_tune_dev.yaml`（19 个点）和
   真实服务器流程检查 `configs/sweeps/p3_smoke.yaml` 已写好。
2. 调参（dev，约 2–3 GPU 小时）：测 16k 容量、定 3 档到达率；选 fixed K* 和 ρ*。
3. 正式实验（test，约 6–8 GPU 小时）：5 种配置 × 3 档到达率 × 2 次重复，tmux 无人值守。

### 4.4 第 3 步调参与余量摸底（2026-11-23）：场景改为 8k

**调参（16k + 默认混合，dev 200，t=0 全部放入，各 1 次；`configs/sweeps/p3_tune_dev.yaml`，`analysis/p3_tune.py`）**：

| 配置 | 最优参数 | goodput | 吞吐 | 失败 | 丢弃 KV | TPOT p50 |
|---|---|---|---|---|---|---|
| fixed K | K=3（K≥4 开始 overflow） | 16.1 | 31.6 | 0 | 0 | 13.3 ms |
| 底座 | ρ=1.5 | 21.2 | 42.2 | 0 | 171 | 24.3 ms |
| + 改文本重算 | ρ=1.5 | 16.8 | 31.4 | 0 | 501 | 35.6 ms |
| + 在 KV 里删（一直删） | ρ=1.5 | 18.9 | 36.2 | 0 | 390 | 30.8 ms |
| + 在 KV 里删（紧张时才删） | ρ=1.5 | 21.8 | 41.3 | 0 | 217 | 27.7 ms |

- 质量：所有删除配置与同 ρ 的底座逐题配对，ΔF1 在 −0.02 到 +0.04，CI 都包含 0（含 `react_short`、`react_explain`）。
- 底座比不出错的最好 fixed K 吞吐高 34%，达到显存充足时上限的约 93%：**这个场景是计算瓶颈**，删除省出的显存
  被准入用来多放 agent，反而让 TPOT 变高（24 → 31 ms）、丢弃变多，所以 selective KV 没有帮助。
- ρ 有陡峭的断崖：1.5 最好，2.0 吞吐减半（丢弃 1,044 次、命中率 76% → 16%）。
- 发现并修复 bug：ρ=1.0 时一个超长任务在等显存时永远等不到（需求 + 共享 prompt 专用 slot > pool），堵住队列 885 s。
  修复后这类请求直接拒绝（只这一个任务记 `ctx_overflow`），见 `KVBudgetExceeded` 和回归测试。

**余量摸底（dev 200，t=0；`configs/sweeps/p3_probe.yaml`）**：上限参考 = 131k pool + fixed K=8。

| 场景 | 上限 | 底座 | 底座 ÷ 上限 | + 在 KV 里删 | 变化 | 失败（底座 / 删除） |
|---|---|---|---|---|---|---|
| 16k + 长任务为主 | 56.1 | 54.2 | 97% | 52.3 | 吞吐 −4% | 0 / 0 |
| 8k + 默认混合 | 45.9 | 33.3 | 72% | 37.7 | 吞吐 +13%，goodput +15% | 12 / 12 |
| 8k + 长任务为主 | 56.1 | 24.8 | 44% | 30.1 | 吞吐 +21%，goodput +18% | 3 / 0 |

- 16k + 长任务为主不是显存瓶颈：长任务每步 prefill 约 2k token，4–5 个 agent 就能占满 GPU（"计算能支撑的并发数"随任务类型变化）。
- 8k 两个场景是显存瓶颈（8k 长任务：TPOT 12 ms vs 上限 32 ms，GPU 大量空闲），selective KV 有效，F1 基本不变。
- 8k + 默认混合的 12 个失败里 11 个是 `oneshot_long`：三份共享 prompt 的专用 slot 永久占 3,114 token（8k 的 39%），
  放不下约 5k 的 `oneshot_long`。

**共享 prompt 的专用 slot 改为可回收的缓存（2026-11-23，`configs/sweeps/p3_golden_check.yaml`）**：
- 请求放不下、且已结束任务和等 tool 的 agent 的 KV 都腾过之后，清掉一个没有 slot 在共享的专用 slot；之后需要时重建。
- 第一版有竞争条件：fork 还没登记时专用 slot 被清掉，fork 出的 cell 不在任何账上 → 真正的 overflow（2 次，8 个任务失败；
  `results/p3_golden_check_v1`）。修复：fork 进行中的专用 slot 不清；fork 完成时专用 slot 已不在，则把 cell 记在该 slot 自己账上。
- 第一版还出现专用 slot 互相挤（360 秒清除 / 重建 36 次）。修复：重建只用"当场能腾出的空间"（已结束 / 等 tool 的 KV），
  不清别的专用 slot、不排队；腾不出就本次不共享（`prime_skipped`）。
- 最终版（8k + 默认混合）：0 overflow、服务器 0 次自行清 slot，失败 12 → 2（剩下 2 个单个任务就超过整个 pool）。

**8k + 默认混合的再测结果**：底座 vs 在 KV 里删 goodput 16.5 vs 16.9，吞吐 32.2 vs 32.1，**优势消失**。摸底时的 +15% 是假象：
11 个最占显存的 `oneshot_long` 当时被拒绝了，剩下的任务跑得更快。它们真正运行后，一个 `oneshot_long`（约 5k，单次请求、
没有可删内容）就占掉 8k pool 的大部分，删 `react_long` 旧检索省下的显存改变不了大局。

**结论**：selective KV 只在**显存是瓶颈、并且 pool 里有足够多可删内容**时有效：
- 计算瓶颈（16k）：无效；不可删任务占比大（8k + 默认混合）：无效；显存瓶颈 + agent 任务为主（8k + 长任务为主）：goodput +18%。

  16k + 30% 第一次测到 +31%，是底座那次陷入循环；摸底里 16k + 长任务的 −4% 是删除那次陷入循环（丢弃 134 次、

**结论**：
- 四种配置都在 ρ=2.0 最好；ρ>2.0 都陷入"丢弃 → 重算"循环（丢弃 347–524 次，TPOT p50 升到 18–25 ms）。
- **同一个 ρ 下删除更好**（ρ 1.0–1.5：+15% 到 +33%），**各自调到最佳 ρ 后分不出高下**（19.0 vs 19.3）。
  §4.4 的 +27% 是对着停在 ρ=1.5 的底座比的，而 1.5 不是底座在 8k 下的最佳值（ρ 是从 16k 调参沿用的）。
  原因：底座把 ρ 调高同样能多放 agent，超出部分由 gate 丢弃、重新 prefill，8k 下重新 prefill 便宜。
  删除的作用是"在更低的 ρ 下就接近最高值、对 ρ 不敏感"，而不是提高最高值。
- **单次运行波动约 10%**：紧张时才删在这个场景里约 330 次删除只推迟 3–5 次，和一直删几乎是同一个配置，
  却差了 11%（21.1 vs 19.0）。所以 ρ=2.0 上四者的差别都在波动内；紧张时才删不进入主实验。
- **和 Phase 1 的做法比**（同一份任务、同一个 8k pool）：底座 ρ2.0 的 goodput 是 fixed K1 的 2.4 倍，吞吐为大 pool
  上限（131k + fixed K=8：53.8）的 69%；fixed K2 为 48%（与 Phase 1 测到的 8k 下 48% 一致），但有 8% 的任务失败。
- F1：配对 ΔF1 的 CI 都包含 0，除了两个单次点：紧张时才删 ρ1.25（−0.043 [−0.084, −0.004]）和删 ρ2.5（+0.042）。
- 底座和删除配置的 1–3 个"失败"都是被拒绝的任务（上下文 8.2k–9.4k，超过整个 pool，`KVBudgetExceeded`），
  不是溢出。`analysis/p3_tune.py` 选最佳参数时不再因为拒绝排除配置。
- 发现：ρ≥2.0 时 KV 管理器账面峰值偶尔超过 pool（最高 12.6k）。原因是 fork 刚完成、记账还没更新时，`_forking`
  已经归零，专用 slot 被 gate 清掉；之后共享同一份 cell 的几个 slot 各记一份。只会多算、不会少算（0 次真溢出），
  但会让 gate 多丢 KV。主实验前修复。
- 过程问题：补跑点的自动启动空等了 20 分钟，因为 tmux 按前缀匹配会话名（等 `p3t8` 时匹配到了 `p3t8b`）；
  以后用 `tmux has-session -t '=name'`。

**主实验设计（2026-11-24，准备中）**：
- test 500 题（350 个 `react_long` + 150 个 `react_short`），8k pool，ρ=2.0（不再调）。
- 配置：fixed K1（Phase 1 做法，不失败的最大 K；每档 1 次，它没有 gate、运行间波动小）、底座、底座 + 在 KV 里删
  （BM25 保留 30%，用过即删）各 3 次。改文本重算不再单独跑（§4.2 和本节已比较）。
- 负载三档按底座的 dev 容量 37.2 任务/分钟定：50% / 80% / 110%，平均 18.6 / 29.8 / 40.9 任务/分钟。

  - 110%：持续超载，比的是容量（goodput）。
  - 原先的随机时段长度只覆盖 6–12 个周期，实际负载变成 57% / 120% / 141%；改为固定时段后 3 组种子都在计划的 ±2% 内
    （`edgeserve/workload.py` 的 `fixed_periods` 选项，已有任务文件不变）。
- **判断规则（开跑前定死）**：goodput 只在 110% 档比较；延迟在 80% 和 110% 档比较全部 500 个任务的 p95 / p99（含排队）；
  "明显"= 两组 3 次均值之差 > 两组中较大标准差的 2 倍；每次重复都报告，不剔除。结果三种情况：删除 goodput 明显更高
  → 能多做；goodput 打平但延迟明显更低 → 能更快；都打平 → 如实写"底座调好后删除无额外收益"，不再调参。
- 开跑前的修复：fork 记账竞争；空闲 KV 占比对底座 / 删除从 `kv_state` 事件算（Phase 1 的 `analysis/kv_timeline.py` 不知道
  丢弃、删除和 fork 共享，对底座 ρ2.0 会算出 20k 峰值），fixed K1 仍用 Phase 1 的工具；sweep 按轮次交错运行
  （每轮 3 配置 × 3 档，共 3 轮）。然后 8k 冒烟检查：账面 ≤ pool、0 溢出、实际负载在计划 ±5% 内、分析脚本出完整表格。
- 报告里写明的限制：ρ=1.75 没试过（删除在 2.0 时丢弃偏多，它的最佳值可能略低）；容量是 dev 上测的，负载百分比以实测为准。

### 4.6 重看 8k 调参、两个修复、16k 快速检查（2026-11-24）

**8k 为什么打平**：按"同时在跑的 agent 数"重看 §4.5 的数据：ρ 只是间接控制并发。删除让预测峰值变小，同一个 ρ 放进的
agent 更多（ρ2.0：删除 4.4 个，已过拐点，丢弃 242 次；底座 3.4 个，丢弃 136 次）。8k 下 GPU 有空闲（TPOT 约 14 ms，约 3 个
agent），底座"超订 + 丢弃 + 重算"几乎不花代价，所以能追上删除；改文本重算也一样（20.1 vs 19.0）。
**删除对调好的底座的优势 = 底座为重算付出的代价**，GPU 闲时接近零。

**否定的想法：加长检索**（`neighbors: 19`）。离线重放：用已有 trace 的检索词重新检索，不用 GPU；方法先用 9 个相关段落验证，
预测删除后峰值 p95 3,990，实测 4,003。结果删除省下的比例不变（峰值 p95 −38% → −34%，平均 −21% → −22%），因为 agent 还没读的
最新检索结果不能删，也一起变长了。

**两个修复**（`edgeserve/kvm.py`；回归测试在 `tests/test_kvm.py`，两个测试在旧代码上都失败）：
1. fork 记账竞争（§4.5 末尾"账面峰值超过 pool"）：fork 对专用 slot 的保护改为在拿锁、记完账之后才解除。
2. 压力判断去掉"有任务在等准入"：准入按预留限制，丢弃或删除驻留的 KV 不会让新任务进来。t=0 全部放入时压力一直成立，
   8k ρ1.0 的 103 次丢弃全是这种（pool 有空也丢）。现在只看"有请求在等显存"或"pool 占用 ≥85%"。
   `--sel-trigger pressure` 的含义随之改变。

**安全**：21 次、10,500 个任务，0 次 server 溢出、0 次 purge，预测从没低于实际。账面峰值 15,880–15,892，等于 pool：
三个托管配置都把 pool 用满。底座有 3 个任务被拒（`KVBudgetExceeded`，3 次运行各 1 个）：一个长任务长到约 16.2k token，
加上专用 slot 永远放不进 16k。删除把它删短了，所以 0 拒绝。

**按事先定的规则**（差距 > 2 倍较大的标准差）：

| 比较 | 底座 | 删除 | 差距 | 判断线 | 结论 |
|---|---|---|---|---|---|
| 110% goodput | 26.8 | 28.9 | +2.05（+7.6%） | 2.81 | 不明确 |
| 110% 延迟 p95 | 60.0 s | 40.6 s | −19.3 s（−32%） | 27.1 | 不明确 |
| 110% 延迟 p99 | 67.6 s | 46.7 s | −20.9 s（−31%） | 23.9 | 不明确 |
| 80% 延迟 p95 | 30.0 s | 23.2 s | −6.7 s（−22%） | 5.2 | **明确** |
| 80% 延迟 p99 | 38.6 s | 28.5 s | −10.1 s（−26%） | 6.2 | **明确** |

逐题配对 ΔF1（删除 − 底座，3 轮合并）：110% +0.016 [0.000, +0.032]，80% +0.012 [−0.004, +0.026]，50% +0.001
[−0.014, +0.017]。都在 ±0.03 内，算不变。

**解读**：
1. **80%：尾延迟明确下降 22–26%，goodput 相同。** 80% 时两边都跟得上到达，goodput 等于到达率乘正确率，只有延迟能拉开。
   延迟差来自等准入的排队，不来自服务时间：110% 时删除的服务时间 p50 反而略长（7.3 vs 6.6 s），因为同时跑的 agent 更多，
   TPOT p50 高 2.5–4.6 ms。删除让同一个 16k pool 放进更多 agent，排队变短（110% 时排队 p95 24–37 s vs 41–68 s）。
2. **110%：3 轮里删除每轮都更好**（goodput +4.0 / +0.6 / +1.6，p95 −34 / −5 / −19 s），但按规则不明确：底座在不同到达序列
   上差别很大（第 1 个序列实测 113% 负载，p95 75.6 s；另两个约 52 s），规则用的是不配对的标准差。按轮配对看 3/3 同方向，
   但 3 对太少，不能算显著。报告写"按事先定的规则不明确，3 轮方向一致"。
3. **goodput 差距（+7.6%）比调参时（+26%）小很多**，原因有两个：
   - 底座在最终代码上快了约 10%（48.5 → 53.5）。冒烟检查的修复让"在 gate 前排队时 KV 被丢掉"的 agent 重新 fork system
     prompt，不再整段重算。这正是删除帮底座省掉的那部分代价（§4.6："删除对调好的底座的优势 = 底座为重算付出的代价"）。
   - 开放到达下 goodput 有上限，就是到达率。110% 时（58.9/分钟）删除跟得上（吞吐 60.0，最后一个任务在最后一次到达后 9–13 s
     完成），goodput 只能等于到达率乘正确率。所以差距只能是底座落后的那部分：吞吐 56.7，最后一个任务在最后一次到达后
     22–44 s 才完成。负载档是按底座在 dev 上的容量定的，底座在测试集上的吞吐（56.7）甚至超过它，所以"110%"对底座只是轻度
     超载。峰值 goodput 要看 t=0 的容量测量。
   - 峰值 goodput 见下面"同一份代码上的容量"。
4. **50%：没有显存压力，打平。** 删除照常执行（触发方式是 `always`，每次运行约 860 次，三档负载都一样），但显存不紧，
   省下来的 KV 用不上。这说明 80% / 110% 的提升来自省下的显存，不是删除本身让每步变快。
5. **和 Phase 1（fixed K3）比**：110% 时删除的 goodput 是它的 1.64 倍，p95 41 s vs 330 s；底座是它的 1.52 倍。80% 时 fixed K3
   已经超载（p95 153 s）。fixed K3 的闲置 KV 占 25–36%（Phase 1 E3：36–44%），托管配置只有 3–11%。
6. 删除的丢弃少一半（110%：55 vs 94；80%：47 vs 111），等显存的总时间也少一半（29 vs 58 s；27 vs 65 s）。TTFT 两边相同。

**同一份代码上的容量**（主实验后补测，用户同意；`configs/sweeps/p3_cap16k.yaml`，`results/p3_cap16k/tune.json`）：
dev 200、t=0 全部放入、16k + 长任务 70%，每个配置 2 次，代码和主实验相同。

| 配置 | goodput | 吞吐 | 服务时间 p50 / p95 (s) | TPOT p50 (ms) | 丢弃 KV | 删除次数 | F1 |
|---|---|---|---|---|---|---|---|
| 底座 ρ1.75 | 27.9 ± 0.4 | 53.5 | 6.2 / 15.7 | 23.1 | 41 | 0 | 0.630 |
| 删除 ρ1.5 | **30.7 ± 0.6** | **59.6** | 6.2 / 14.4 | 24.2 | 1.5 | 352 | 0.628 |

- 按事先定的规则：**goodput +2.84（+10.2%），判断线 1.24，明确**；吞吐 +11.5%。逐题配对 ΔF1 −0.002 [−0.041, +0.038]。
  这里只有 200 题，所以 CI 宽；主实验 1,500 对的结果（+0.001 到 +0.016）更有说服力。
- 删除修复前后不变（30.8 → 30.7），底座从 24.5 涨到 27.9，所以峰值差距从 +26% 缩小到 +10%。这和"删除的优势 = 底座为
  重算付出的代价"一致：冒烟检查的修复减少了底座的重算。报告的峰值 goodput 用这里的 +10%（同一份代码），+26% 不再作为结论。
- 删除的容量 59.6 和主实验 110% 档的平均到达率 58.9 几乎一样，所以 110% 档对删除来说正好在它的容量边上，对底座是轻度超载
  （110%）。这也解释了为什么 110% 档 goodput 的差距只能很小。
